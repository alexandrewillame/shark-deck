# Adding a device model

Cheaper than adding a capability: the descriptor pattern genuinely works. **4
required files, 3 conditional.** Most of the wiring is automatic - the list of
what you do *not* have to touch is below, and it is worth reading so you do not
go looking.

## Required

### 1. The descriptor

New file `app/src/main/devices/catalog/<model>.ts`. Copy the closest existing
one - `v8.ts` for a mouse, `r85he.ts` for a magnetic keyboard - and change the
identity, `capabilities[]`, and `spec`.

Pick `driver` from the three registered in
`app/src/main/devices/drivers/index.ts`: `compx-mouse-8k`, `compx-keyboard`,
`compx-he-keyboard`. A genuinely new protocol means a new driver, which is a
much bigger job than this checklist.

Set `provenance` to `verified-capture`, `ported-from-vendor`, or `inferred`
honestly. Only V8 profile switching is `verified-capture`; assume anything you
have not captured is `inferred` and keep the read-back diff.

### 2. The catalog slot

`app/src/main/devices/catalog/index.ts` - one import and one array entry in
`CATALOG`. Twelve lines total; the file's own comment describes this as the
whole job, which is nearly true.

### 3. Device art

Drop a `.webp` in `app/assets/devices/`, roughly 800x800, under ~100 kB.
`app/assets/devices/README.md` has the art conventions.

### 4. Wire the art up

`app/src/renderer/components/deviceArtAssets.ts` - a static `import` at the top
plus an entry in `DEVICE_ART` (and `DEVICE_ART_DETAIL` if the model has a
receiver LED, DPI indicator, or side lighting you illustrate).

**The imports must be static.** The renderer CSP forbids fetching, so the art
has to go through the bundler.

**Filename trap:** the R85HE's files are `attack-shark-r85-he-*.webp` while its
model slug is `attack-shark-r85he`. The filenames and the slug do not have to
match, and for that model they do not. See the comment at
`deviceArtAssets.ts:26-30` before assuming a naming rule.

`app/src/renderer/components/deviceArt.test.ts` walks `CATALOG` and asserts
every declared variant resolves, so a missing entry fails the unit tier.

## Conditional

| When | File | Change |
|---|---|---|
| The model has named colour/edition variants | `app/src/shared/i18n/en.ts` + locales | `color.<model>.<variant>` labels. Use `npm run i18n:add`. |
| The PID should fall back to a *generic* profile rather than this exact entry | `app/src/main/devices/catalog/known-pids.ts` | **Read the header first.** It is `AUTO-EXTRACTED - do not edit`, regenerated by `npm run extract`. An exact catalog entry does **not** need a `known-pids` line; the older claim that every model needs one is wrong. |
| You want it in the reference catalogue | `docs/devices/attack-shark-lineup.md` | The "Supported today" table. Secondary to the real descriptor, easy to forget. |

## Free by construction - do not go looking for these

- **A simulated device.** `virtualDescriptors()` in
  `app/src/main/devices/virtual.ts` spreads `...CATALOG`, so the new model shows
  up in developer mode automatically. You only need a read seed if you also
  added a *capability* (see the `add-capability-tab` skill).
- **USB vendor matching.** `knownVendorIds()` in
  `app/src/main/devices/registry.ts` derives the VID list from the catalog.
- **Firmware model-id disambiguation.** `resolveModelId()` in `registry.ts`
  already handles the ~99 boards that share `3151:5029`.
- **Config tabs.** `configTabs()` derives them from `capabilities[]`.
- **The udev rule.** `app/assets/linux/60-sharkdeck.rules` is checked against
  `knownVendorIds()` by `app/src/main/hid/udev-rules.test.ts`. A new **VID**
  (not PID) means updating the rule, and that test will tell you.

## Verify

```bash
cd app && npm run --silent check
```

Then with the real device connected:

```bash
cd app && node scripts/smoke-hid.mjs
```

Read-only, ~8-10 lines per device: path, serial, profile, battery, firmware.
It walks hardcoded targets by default, so use `--probe <vid>:<pid>` for a model
it does not know yet. **Never pass `--watch`** - it re-enumerates forever and
never exits.

No hardware? `npm run dev`, then Settings -> Developer -> **Simulated devices**
(unpackaged builds only) - the new model should appear in the home grid with
its art, and every tab its capabilities imply should read a plausible value.
